Fabro workflow · security-review

How the security review works

An adversarial, read-only security review of a repository. Agent teams map the code, hunt for vulnerabilities, and then try to destroy each other's findings. Only findings that survive a three-voter panel reach the report.

See an example report →

Reference

Inputs

Seven inputs, all optional except when a mode demands one. The prepare step validates every combination and rejects contradictions (for example, scan mode with a base).

modescanall scan reviews the tree as it is. changes reviews a branch diff. commit reviews one commit against its parent.

1 · Map

Prepare

script 180 s

Deterministic setup, no model involved. It verifies the SHA-256 hashes of the driver scripts and report spec before running anything, validates the input combination, resolves the Git range, counts changed files and lines, and decides the run shape. It creates the SECURITY-REVIEW-<timestamp>/ output directory and snapshots a digest of every file in the tree — the tamper check used before publishing.

Shape decision: low effort, a small diff (≤ 5 files and ≤ 300 lines at medium), or a small scope (≤ 5 files at medium) collapses the run to a single-researcher shape. Everything else runs the full component-matrix. Any deterministic failure from here on routes to abort, which stops the run.

◇ Target has work?

Inventory

agent kimi-k3 · low

One cartographer agent partitions the repository into components — an HTTP API, a background worker, a parser — without hunting for bugs. It returns two ledgers: components to scan and securityScanSkippedComponents with a reason for each skip. On a whole-tree scan, every top-level directory must land in one of the two lists.

A deterministic completeness check follows. An incomplete answer gets exactly one correction pass with pointed feedback; a failed agent falls back to scanning the whole target as a single component, so nothing silently disappears. Each attempt has a 60-minute timeout.

script

Research

agents kimi-k3 · high

The four category lenses: injection & input handling, auth & access, memory & unsafe operations, and crypto & secrets. The memory lens is pruned for components written entirely in managed languages (Python, TypeScript, Ruby, Java, …). Gap-fill sweeps

agents kimi-k3 · high

Sweeps hunt where the component matrix has blind spots. The phase has a concurrency cap of 12 and a 180-minute timeout per attempt:

  • Glue sweep — entry points and sinks outside covered paths: scripts, CI definitions, migrations, admin tooling.
  • Boundary sweep (high/max only) — bugs between components: a value validated in one and trusted in another.
  • Secrets sweep (focused scans only) — hardcoded credentials anywhere, tests and fixtures explicitly included, because a real key in a fixture is a real leak.

3 · Judge

Deduplicate & rank

script caps: 400 ledger · 45 verified

Every finding gets a stable fingerprint derived from the target, its ruleId, and its identity slugs — so a line move does not create a new finding. Duplicate reports merge; the count of independent reporters is kept as corroboration. Candidates are ranked by severity, then report count, then confidence. The top 400 enter the ledger; the top 45 go to the panel. Everything past a cap is recorded as deferred, never silently dropped.

Three-lens panel

agents kimi-k3 · high

Three independent voters per candidate, up to 24 in parallel, with a 120-minute timeout per attempt. Each voter is assigned one refutation lens: reachability (is the source really attacker-controlled?), impact (does it really do the claimed damage?), and defenses (does something already stop it?). Voters see only the reporter's claim and cited evidence — the confidence, impact story, and exploit scenario are withheld so they can't anchor the vote. The default verdict is FALSE_POSITIVE; a candidate needs all 3 votes returned and at least 2 TRUE_POSITIVE to survive.

◇ Max effort?

Repanel marginal keeps

agents kimi-k3 · high

Runs only at max effort. Any candidate that survived on a marginal 2-of-3 vote faces three fresh voters with the same lenses (using the same verify.md.j2 prompt). Fewer than 2 TRUE_POSITIVE on the recheck drops it. An incomplete repanel leaves the first verdict standing and records the casualty in the coverage report. The phase runs up to 24 voters in parallel, with a 120-minute timeout per attempt.

Red team

agents kimi-k3 · high

Runs only at max effort. One dedicated refuter per surviving finding, up to 24 in parallel, with a 180-minute timeout per attempt. Each refuter considers reachability, impact, and defenses together. The burden flips here: the refuter must locate a real, citable reason the claim is a false positive; if it tries in earnest and cannot break it, the finding stands.

4 · Publish

Final tally & report

script tamper check · canonical bundle

Before publishing anything, the driver re-hashes every file in the tree and compares it to the digest taken at prepare — if the reviewed source changed during the scan, it refuses to publish. It then writes the canonical bundle and renders the human-readable report: 

SECURITY-REVIEW-<timestamp>/
├── .gitignore
├── SECURITY-REVIEW-RESULTS.md       # the report — panel-verified findings only
├── SECURITY-REVIEW-RESULTS.html     # the same report as one self-contained page
├── SECURITY-REVIEW-RESULTS.jsonl    # the same findings, machine-readable
├── evidence/
│   ├── scan-manifest.json           # run identity, request, completion status
│   ├── findings.json                # kept findings, canonical form
│   ├── candidate-ledger.jsonl       # every candidate and disposition
│   ├── coverage.json                # what was scanned, skipped, pruned, capped, and why
│   └── panel-votes.jsonl            # every vote, lens, verdict, and reasoning
└── metadata/
    ├── revision.json                # reviewed revision and run settings
    ├── state.json                   # deterministic workflow state
    └── scan-meta.json               # scan setup and target identity

See an example of that HTML report → — built from fictional findings. Its finding index supports search and component, severity, and difficulty filters.

Fabro publishes every security-review artifact under this one result directory. The reports stay at the root. Canonical evidence and run metadata use their own directories.

Reported confidence is capped by the vote: a unanimous 3-of-3 keep may report up to high confidence; a 2-of-3 keep is capped at medium. The renderer re-checks that cap against the recorded votes, so an edited bundle cannot claim more than its panel earned.

Each finding carries a severity and a difficulty. Severity describes impact. Difficulty describes the access, knowledge, and effort exploitation takes, so low difficulty is the worse case. The excerpt shown with a finding is read from the reviewed tree by the same deterministic step, never transcribed by an agent, so its line numbers are the tree's own.

Reference

What effort buys

Effort is the main throttle. It never relaxes verification — every reported finding is panel-verified at every tier — it changes how wide the hunt fans out and how many adversarial rounds survivors must endure.

EffortShapeComponent capResearchers per cellGap sweepsVerification rounds
lowsingle researcher—1 total0panel
mediummatrix (collapses to single for a small diff or scope)1211panel
highmatrix, always2422panel
maxmatrix, always2422panel + repanel + red team

The secrets sweep is orthogonal to effort: it runs on any focused scan, even a single-researcher one. Focused means focus=attack-surface — set explicitly or triggered automatically by a scan of more than 500 files. A separate workflow-wide stall watchdog stops the run after four hours without an event.

Verification math

What survives

Every candidate faces three voters who are told to disprove it and to default to false positive. The arithmetic:

3 / 3 true Kept. Reported confidence may go as high as the reporter claimed.
2 / 3 true Kept, confidence capped at medium. At max effort: three fresh voters recheck it; fewer than 2 true on the recheck drops it.
≤ 1 / 3 true Dropped. Recorded in the ledger as panel-rejected, with every vote's reasoning.
< 3 votes Not kept. A candidate with an incomplete panel is never reported as verified.
red team Max effort only: one last refuter per survivor. It must cite a concrete reason to kill the finding — trying and failing means the finding ships.
